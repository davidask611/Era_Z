PROYECTO: JUEGO DE SUPERVIVENCIA ZOMBIE
Python + Ursina + Toon + Pygame
Plan de trabajo para David y su amigo

==================================================
1. IDEA GENERAL
==================================================

La idea es desarrollar entre dos personas un juego de supervivencia con zombies usando Python, Ursina, Toon y Pygame.

Cada uno trabajará desde su propia PC y el proyecto estará alojado en GitHub.

Los dos tendrán una copia completa del proyecto en su computadora, pero cada uno trabajará principalmente sobre sus propios módulos y archivos.

La finalidad es reducir conflictos y poder desarrollar distintas partes del juego al mismo tiempo.


==================================================
2. GITHUB COMO CENTRO DEL PROYECTO
==================================================

GitHub será el repositorio central.

Los dos tendrán:

- Una copia local del proyecto.
- El mismo código base.
- Acceso al repositorio de GitHub.
- Sus propias ramas de trabajo.

NO es recomendable que los dos trabajen directamente sobre main.

Ejemplo:

                    GITHUB
                       |
             +---------+---------+
             |                   |
          PC DAVID           PC AMIGO
             |                   |
          rama david           rama amigo
             |                   |
          sus módulos         sus módulos


==================================================
3. RAMAS
==================================================

Se recomienda tener:

main
david
amigo

La rama main representa la versión estable del juego.

David trabaja principalmente en:

david

El amigo trabaja principalmente en:

amigo

Cuando una parte está terminada y probada, se puede integrar a main mediante un merge o Pull Request.

Ejemplo:

david --------------------+

amigo --------------------+

7. REGLA PRINCIPAL
==================================================

Cada uno debería trabajar principalmente en sus propios archivos.

Ejemplo:

David:

mundo/casas.py
mundo/agua.py
clima/lluvia.py
clima/tormenta.py
vehiculos/vehiculo.py

Amigo:

zombies/zombie.py
zombies/administradorZombies.py
mundo/arboles.py
armas/arma.py
jugador/inventario.py


De esta forma es mucho menos probable que Git encuentre conflictos.


==================================================
8. EVITAR MODIFICAR LOS MISMOS ARCHIVOS
==================================================

Los archivos que deberían tocarse con más cuidado son los archivos centrales.

Por ejemplo:

main.py
jugador/jugador.py

Si los dos modifican las mismas líneas al mismo tiempo, Git puede generar un conflicto.

En ese caso tendrán que revisar los cambios y decidir qué código conservar o combinar.


==================================================
9. COMUNICACION ENTRE MODULOS
==================================================

Cada módulo debería tener una interfaz sencilla.

Por ejemplo, el sistema de zombies podría permitir:

zombie = Zombie(posicion=(10, 0, 20))

y:

zombie.recibirDanio(25)


El sistema de vehículos podría permitir:

vehiculo = Vehiculo(posicion=(20, 0, 10))

y:

vehiculo.entrar(jugador)


La idea es que cada persona pueda usar el sistema del otro sin tener que modificar cómo funciona internamente.

Esto permite que los módulos sean independientes.

==================================================
MEJORAS RECOMENDADAS LUEGO DE LA REVISION
==================================================

1. Integración temprana
- No dejar la integración para el final.
- Tener un main.py mínimo que ambos puedan ejecutar desde temprano.
- Integrar una parte pequeña a la vez para detectar errores rápidamente.

2. Interfaces entre módulos
- Definir pronto los contratos:
  - zombie.recibirDanio(daño)
  - vehiculo.entrar(jugador)
  - inventario.anadir(item, cantidad)
- Cada módulo debe poder usarse sin modificar su funcionamiento interno.

3. Multijugador
- Si el juego será multijugador, definir cliente/servidor desde el principio.
- Si aun no es seguro, conviene empezar en un solo jugador y dejar preparado el código para expansión posterior.

4. Archivos pesados
- No subir modelos, texturas o sonidos grandes al repo normal.
- Usar Git LFS o guardarlos fuera del repositorio y sincronizarlos aparte.
- Mantener el repositorio ligero y rápido.

5. .gitignore más completo para Python
- Agregar desde el inicio:
  venv/
  __pycache__/
  *.pyc
  .idea/
  .vscode/
  *.log
  *.tmp
- Evitar subir entornos virtuales y archivos temporales.

6. Pruebas pequeñas
- Cada módulo debería tener una forma de probarse por separado.
- No subir código que no se pueda ejecutar ni revisar.

7. Versión estable
- main debe representar siempre una versión estable.
- Trabajar cambios en ramas personales.
- Integrar a main solo cuando una función esté probada.

8. Comunicación
- Avisar antes de modificar archivos centrales como:
  main.py
  jugador/jugador.py
- Evitar conflictos revisando periódicamente el estado del repositorio.

9. Orden recomendado para empezar
1. Clonar repositorio.
2. Crear ramas personales.
3. Crear estructura de carpetas.
4. Configurar Python y Ursina.
5. Crear jugador y movimiento.
6. Crear una isla mínima.
7. Agregar día/noche básico.
8. Integrar primero código de ambos en main.

10. Objetivo práctico
La meta no es hacer dos juegos distintos e intentar pegarlos después.
La meta es construir un solo juego modular, donde cada persona desarrolla sistemas independientes que luego se conectan.
